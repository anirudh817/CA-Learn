AI Insights Tab — Design Document

A run-scoped, persistent, multimodal chat embedded as a tab inside a completed run's results view. Scientists ask biological questions in plain language; answers stream token-by-token, are grounded in the run's own artifacts, cite their sources, track cost, and refuse to leak product internals. This document traces the feature end-to-end — from the DOM in frontend/index.html through chat.js and the SSE wire to the FastAPI turn pipeline.

What the AI tab is

The AI tab ("✦ AI Insights") is one of the tabs in a run's results view — not a standalone page. Opening it binds the chat to the currently-open run (frontend/app.js:1128), so every conversation is scoped to one run's data, which the backend reads as a read-only black box. The UI is a three-column shell: a conversation list, the message thread with a streaming composer, and a collapsible context panel for browsing and pinning the run's artifacts.

It is not a general chatbot and not a place to inspect pipeline internals — a confidentiality layer actively refuses to disclose methodology, source, or model identity. v1 is Anthropic-only; users bring their own key or draw on a quota-limited platform key.

  • Start/rename/delete/clear conversations, each pinned to a run.
  • Ask a question and watch the answer stream, with live tool-call breadcrumbs.
  • Attach files/images (drag, paste, or picker) and @-mention or pin run artifacts as context.
  • See per-answer provenance (Grounded / External / Background) and a "what sourced this" panel.
  • Enable opt-in external biology lookups (UniProt/Reactome/STRING/PubMed) after a consent step.
  • Manage the Anthropic key, model, and (as admin) workspace lookup policy in a settings drawer; watch session cost and platform-quota gauges.

Entry & run binding

The tab button APP.tab('ai', event) (index.html:1076) shows #tab-ai and calls APP.chat.bindToRun(STATE.currentRunId) (app.js:1128). bindToRun(runId) (chat.js:2427) loads that run's conversations via GET /api/runs/{runId}/conversations and auto-opens the most recent one (or shows the starter prompts if none). With no run open, the shell hides behind #chatEmptyHint ("Open a completed run to chat about it."). APP.chat.init() runs once from a patched APP.init (app.js:1242) to wire all the static buttons, the scroll listener, drop/paste, and modal a11y (Escape + focus-trap).

The happy path: send → stream

The composer uses a raw streaming fetch + ReadableStream reader — not EventSource — because the turn is a POST with a JSON body and a Bearer token, which EventSource can't send. The reader splits on the SSE frame delimiter and dispatches each data: line by type. The UI is optimistic (the user bubble and a "Thinking…" indicator appear instantly) but the server stays canonical: after the stream ends, the client re-fetches the full conversation so persisted IDs, citations, and cost replace the streamed approximation.

  1. Keystroke — Enter (no Shift) in #convInput hits the keydown handler (chat.js:2405) which calls sendMessage(). The @-mention dropdown gets first refusal on Enter/arrows/Esc.
  2. Guard + optimistic render — sendMessage (chat.js:1718) trims input, creates a conversation if none, binds convId, and bails if streams.isActive(convId) (the per-conversation double-send guard, chat.js:1734). It pushes an optimistic user bubble and calls streams.start(convId, AbortController) (chat.js:1752).
  3. Streaming request — fetch(POST /api/conversations/{id}/messages) with Accept: text/event-stream and body {content, attachment_ids, pinned_refs} (chat.js:1776).
  4. Server gates + context — send_message (conversations.py:1047) sees _wants_stream (:926), runs the input security gates, calls build_provider_messages (context_builder.py:626), and enters _stream_assistant_turn (:1492).
  5. Tool loop + stream — up to MAX_TOOL_ITERATIONS = 4 (conversations.py:1470) provider rounds; AnthropicProvider.stream yields deltas (each scrub_output-ed) and tool calls.
  6. Client projection — the reader loop (chat.js:1809) routes each event into chatStreams and, if on-screen, paints: deltas into the streaming bubble, tool calls into breadcrumbs, usage into the meters.
  7. Output gate — heuristic_output_leak (fail-CLOSED) + the output judge run before finish; a confirmed leak emits redacted instead.
  8. Finalize + reconcile — on stream end, finalizeStreaming (chat.js:1908) renders the action bar/provenance, then a convId-scoped GET /api/conversations/{id} reloads canonical messages and refreshList updates the sidebar.

SSE event contract & UI projection

The server defines the wire. There are three SSE generators: an input-refusal stub (conversations.py:1018), an early auth-error path (:1188), and the main turn (:1533). Per-conversation stream isolation

This is the feature's defining UI decision, born from a real bug: streaming used to write to one shared set of globals and paint directly into the thread, so opening another conversation mid-stream bled tokens into it and then blanked it. Now chatStreams.js:17 keys all accumulation by convId; every DOM write is gated on _isOnScreen(convId) (chat.js:760). Switching into a live conversation calls reprojectStream (chat.js:861) to rebuild its breadcrumbs and bubble from accumulated state. Conversations now stream concurrently and independently, and the post-stream reload is convId-scoped so a background finish can't overwrite the visible thread.

Backend turn pipeline

Behind the SSE, send_message enforces defense-in-depth. Input passes a rolling rate limiter and a regex extraction blocker (security.py) before any model call, plus an optional fail-open Haiku intent judge. build_provider_messages assembles history (compressed past 70% of budget), schema-aware retrieval over the run's artifacts, attachments (wrapped as untrusted), and pinned refs. The tool loop is hard-capped at 4 iterations; tools read only run data — internal-methodology files are blocked. Every answer is scrubbed and run through the deterministic heuristic_output_leak backstop before finish; a confirmed leak becomes a redacted event.

Augmenting a turn: attachments, mentions & pins

Attachments stage in the composer before send: uploadAttachmentFiles (chat.js:1003) pre-flights extension/size caps locally, builds image thumbnails optimistically, then POSTs multipart to /conversations/{id}/attachments; their IDs ride the next message. Drag-drop and clipboard paste route to the same function (chat.js:1129). Two-tier pinning: an @-mention (getActiveMention, chat.js:1417) adds a per-turn ref to pendingRefs; the context-panel pin button (togglePersistentRef, chat.js:1333) PATCHes pinned_refs onto the conversation so it rides every turn. Both render as chips in #convPinnedStrip. On a failed send, staged attachments and pins are preserved (cleared only after a 200, chat.js:1804).

Settings, BYOK & quota

The gear opens #aiSettingsDrawer; openSettings (chat.js:2071) loads GET /settings/ai + /providers and (for admins only — members get 403) the workspace AI policy. renderSettingsDrawer (chat.js:2193) shows the model select, a masked key-status card, a paste field, "Test connection" (a 1-token ping to /settings/ai/test), and the admin block (external-lookups policy + per-adapter usage bars). Keys are stored encrypted and never returned. The UI surfaces key provenance: a usage event's key_source drives the quota gauge, which only appears when the last turn actually consumed platform budget.

Provenance, discovery & follow-ups

These three features all answer one question — how was this answer derived? Provenance exposes the answer's basis; Discovery mode changes how the answer is derived; follow-ups propose what to ask next. They are mechanically distinct, so this section traces each.

1 · Provenance — how the answer's basis is derived

The badge is not something the model declares — it is computed from two independent data streams that the server attaches to the assistant message, then interpreted by the client. Understanding provenance means understanding those two streams:

  • Citations (citations_json) come from build_citations() (context_builder.py:887), computed at turn start (conversations.py:1273). When the conversation is bound to a run, it re-runs the same retrieval that grounds the answer — heuristic_intent(question) then retrieve(index, intent) — and collects each retrieved chunk's .citations (a file_path plus the contributing row_ids). If retrieval yields nothing it falls back to stage1/volcano_results.tsv; attachments are cited as attachment:{filename}; and explicitly pinned/@-mentioned run artifacts are appended as citations (conversations.py:1275). So citations describe the run data that was put in front of the model.
  • Tool calls (tool_calls_json) are the agentic calls the model actually made, accumulated into accumulated_tool_calls during the loop (conversations.py:1542) and persisted at conversations.py:1563. Each carries provenance metadata: run-data tools record cited_files, rows_returned, latency_ms (conversations.py:1736); external lookups instead record references (URL + label) and a cached flag (conversations.py:1712). So tool calls describe what the model actively pulled, live.

The client classifies that union into three non-exclusive tiers in provenanceBadge() (chat.js:308) — a single answer can be both Grounded and External:

BadgeShown whenMeans
Groundedany citations or any non-external tool callat least one claim is traceable to this run's data
Externalany tool call with external: truea live public-database lookup contributed
Backgroundneither of the abovedrawn from model knowledge; nothing cited
Errormessage status === "error"the turn failed to produce a grounded answer

The expandable "What sourced this answer?" panel (renderProvenancePanel(), chat.js:333) renders the same two streams in detail: files cited (with row IDs), run-data tools (args + rows + latency), external sources (references deduped by URL, each openable), and attachments used. Two confidentiality mechanics hold even here: breadcrumbs and citations show the public database name via extDbName() (chat.js:302 — e.g. lookup_uniprot → "UniProt"), never the internal tool name; and every external link passes through safeHref() (chat.js:1107), a scheme allowlist that collapses javascript:/data: URLs to #.

2 · Discovery mode — how it changes the derivation

Discovery mode turns the assistant from a question-answerer into an interpreter of the whole run. The conversation-scoped gate is discovery_active(conv, user_content) (context_builder.py:230): on always fires, off never does, and auto (the default) fires only when the user's text matches a synthesis-intent pattern — "biologically", "mechanism", "interpret", "hypothesis", "what does this mean", etc. (DISCOVERY_INTENT_PATTERNS, context_builder.py:213). When active, two things change about how the answer is derived:

  • The system prompt swaps from v2 to v3 (conversations.py:1270 → system_prompt("v3"), context_builder.py:207). V3 (context_builder.py:192) appends interpretive rules: lead with the biological story; separate grounded run-derived numeric claims from background biology (which must be labelled [background]); never infer a missing evidence layer — say it is unavailable; and close with What this suggests + Open questions sections.
  • An artifact-grounded "biological landscape" is injected as a context block (build_provider_messages adds it at context_builder.py:809). build_biological_landscape(run_id) (context_builder.py:457) assembles it from run artifacts only: run metadata (manifest), the top-25 DE signals (volcano, sorted by adjusted p-value), top-10 GO enrichments, top-10 CellTypeFET associations, and top-10 module-trait relationships. Crucially, any missing layer is written as an explicit _Not available_ marker — the anti-hallucination mechanic that stops the model inventing GO/cell-type results the pipeline never produced.

So Discovery mode never fabricates interpretation: it pre-computes a sourced summary of exactly what the run contains (and what it lacks) and instructs the model to reason over that, labelling everything beyond it as background.

3 · Follow-ups — how the next questions are generated

Follow-up chips are not part of the main answer — they are produced by a separate, deliberately cheap call after the answer has fully streamed and only if it was not redacted (conversations.py:1942). generate_followups() (context_builder.py:841) makes a one-shot provider.complete() on Haiku (claude-haiku-4-5, max_output_tokens=300) under a tight system prompt, FOLLOWUP_SYSTEM (context_builder.py:831): return only a JSON array of three questions, each under 90 chars, ending in "?", no yes/no, no "what does this mean". The call is fed the original question (recovered by scanning the turn's messages in reverse for the last user text, conversations.py:1946) and the answer text (truncated to 6,000 chars). The result is parsed (code-fence-stripped), capped to three, and emitted as a trailing followups SSE event (conversations.py:1962). Any failure returns [] — follow-ups are pure polish and must never block or break the main turn.

On the client, followupChipsHtml() (chat.js:421) renders each as a clickable chip carrying its data-question; clicking simply calls sendMessage(question), so a follow-up is just a pre-filled next turn. (Long markdown tables in any answer auto-collapse past 10 rows with a "Show all" toggle — applyTableCollapsing(), chat.js:662.)

UI design decisions

  1. Run-scoped tab, not a global chatbot established 2026-05

    The chat is a tab inside a run's results and binds to STATE.currentRunId (app.js:1128). Every conversation is anchored to one run's artifacts, which keeps answers grounded and retrieval cheap. The cost: cross-run questions need the explicit "Other runs" context tab.

  2. Per-conversation stream isolation established 2026-06-18

    Streaming accumulation moved from shared globals into a per-convId registry (chatStreams.js); the DOM became a projection gated on _isOnScreen. This fixed a token-bleed bug and made conversations stream concurrently. The pure, DOM-free registry is unit-testable without a browser.

  3. Streaming fetch + reader, not EventSource established 2026-05

    The turn is a POST with a JSON body and Bearer auth, which EventSource cannot express. The client reads the response stream and parses SSE frames by hand (chat.js:1809), and gets AbortController-based Stop for free.

  4. Optimistic UI, server-canonical reconcile established 2026-05

    The user bubble and a "Thinking…" indicator appear instantly and the answer streams live, but a convId-scoped GET reloads the persisted turn afterward so real IDs, citations, and cost replace the streamed approximation.

  5. Redacted answers are terminal at the UI layer established 2026-06-18

    A redacted event is rendered as an error notice and explicitly never re-rendered as a grounded answer with provenance/regenerate (chat.js:908). Security is enforced in the projection, not just the server.

  6. Provenance as first-class UI established 2026-06

    Grounded/External/Background badges plus a "what sourced this" panel make the answer's basis legible. Breadcrumbs name the public database, never the internal tool — the confidentiality boundary is honored even in the UI affordances.

  7. Two-tier pinning + preserve-on-failure established 2026-06

    @-mentions pin for one turn; context-panel pins persist on the conversation. Staged attachments/pins survive a failed send (cleared only after a 200), so an error never makes the user re-attach.

  8. BYOK-first with quota-aware nudges established 2026-05

    Key precedence (user → workspace → platform) is surfaced: the quota gauge shows only when a platform key was used, and a 429 renders an "add your own key" card rather than a bare error.
