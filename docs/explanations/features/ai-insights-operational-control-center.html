A developer-only, read-only view over the canonical Pi sidecar. It makes prompt composition, grounding selection, Pi message flow, tool and Python execution, persistence, usage, and terminal outcomes inspectable without creating a second inference path.

Outcome and recommendation

The best shape is a separate route on the same sidecar, not a parallel backend. The implementation serves /operations only when both developer mode and the operations flag are enabled. It polls read-only summary/detail APIs and reads structured events written by the same request and runtime path that produces the researcher-visible answer.

Architecture and protection boundary

loadConfig() defines the switches at ai-sidecar/src/config.ts:46. buildServer() computes the effective gate at ai-sidecar/src/server.ts:61. When disabled, the static route is never registered, every operations API returns 404, and new turns do not create operational records. Existing researcher chat behavior stays on the same path.

One turn, one trace

  1. Accept and classify. ai-sidecar/src/server.ts:231 starts a bounded operational turn after the normal run/conversation/model checks and records the security decision.
  2. Select grounding. FilesystemRunCatalog.groundingSnapshot() at ai-sidecar/src/run-catalog.ts:80 returns the exact included file manifest, byte budget, included bytes, and truncation state.
  3. Compose and hash. PiRuntime.turn() at ai-sidecar/src/runtime.ts:83 records the scrubbed prompt capture, SHA-256, explicit capture-limit state, history restoration, policy, source permissions, and section sizes before dispatch.
  4. Observe Pi. ai-sidecar/src/runtime.ts:176 emits internal OperationRuntimeEvent frames; the server persists those frames but never forwards the internal operation envelope to researcher chat.
  5. Finish canonically. Usage, assistant persistence, terminal status, error text, and duration are attached to the same turn record in ai-sidecar/src/store.ts:228.

How grounding validation works

Grounding is validated at the moment evidence is assembled, rather than inferred later from the answer. The trace shows every selected run-relative file, how many bytes existed, how many reached the prompt, and whether the excerpt was cut. The Prompt view then proves that those excerpts were actually present in the composed Pi input. The answer’s file citation can therefore be checked against both selection and dispatch.

candidate output → grounding_selected.files[]
selected excerpt → prompt_composed.prompt
Pi/provider flow → pi + message timeline events
saved answer → assistant_message_saved
grounding claim → compare citation with the two records above

Security, privacy, and retention

  • Off means off: set AI_OPERATIONS_CENTER=0 or AI_DEVELOPER_MODE=0. Routes disappear and new operational recording stops.
  • Bounded retention: AI_OPERATIONS_RETENTION_TURNS=100 keeps the newest turns and cascades deletion of older event rows.
  • Structured scrubbing: credential-shaped keys, key values, provider environment assignments, and host-absolute user paths are redacted before persistence by ai-sidecar/src/security.ts.
  • Read-only surface: no replay, mutation, delete, model-call, or execution endpoint exists under /api/operations/*.
  • Local sensitivity: prompts may contain run evidence. Disable the center and apply normal data-directory controls before production use.

Important runtime truth exposed

current gap The sidecar advertises four Python skills, while the real Pi session is currently constructed with tools: []. Consequently, Python is configured as developer-local, but no execution tool is registered and those advertised skills cannot run. The control center deliberately reports these as different states: advertised skills, discovered Pi skills, registered Pi tools, and observed executions.

This feature instruments future skill_start/end and python_start/end frames now, but it does not silently add shell authority or pretend current execution exists. Wiring an approved bounded execution backend remains a separate implementation milestone.

Verification and operator workflow

  1. Enable locally. Keep AI_DEVELOPER_MODE=1 and AI_OPERATIONS_CENTER=1 in ai-sidecar/.env, then restart the sidecar.
  2. Open the center. Use the Operational control center link in AI Insights or navigate to http://127.0.0.1:4317/operations.
  3. Send a normal turn. Watch the turn appear as running; inspect Prompt and Grounding after composition, then Outcome and Execution at completion.
  4. Validate grounding. Confirm the cited run-relative file appears in the grounding manifest and composed prompt capture; if the capture limit was reached, use the full-prompt SHA-256 for correlation.
  5. Disable for release. Set either gate to 0, restart, and verify /operations plus /api/operations/turns return 404.

Automated evidence lives in ai-sidecar/tests/server.test.ts:140, disabled-mode coverage at ai-sidecar/tests/server.test.ts:171, grounding snapshot coverage in ai-sidecar/tests/run-catalog.test.ts:19, and structured scrubbing coverage in ai-sidecar/tests/security.test.ts:11.
