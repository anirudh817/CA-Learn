0 · How to read this

SignalFold's AI Insights chat is not built on a bespoke LLM loop. It embeds Pi — a minimal, embeddable coding-agent harness from @earendil-works/pi-coding-agent — through Pi's SDK. So to understand the sidecar you must first understand Pi, and the cleanest way to learn Pi is to watch a real integration use it. That is the bargain of this document.

By the end you will be able to answer four questions precisely, each grounded in source:

  • What is Pi and how does the sidecar talk to it? → §2, §3
  • How does one prompt become a loop of model calls and tool calls? → §4
  • How does code get generated, and how does Python actually run? → §5, §6
  • How do skills get pulled in — and why are they inert in the sidecar today? → §7, §9
Mental model

Pi is to an LLM what a shell is to a kernel. The model is the decision-maker; Pi is the harness that gives it tools (bash, read, write, edit…), feeds it context (a system prompt, skills, files), runs an agentic loop (call model → run the tools it asked for → feed results back → repeat), and emits a stream of events. The sidecar supplies the model, the API key, the working directory, and the grounding text — then listens to the event stream and turns it into Server-Sent Events for the browser.

1 · The two-process picture

SignalFold is a FastAPI/Python monolith (the proteomics pipeline, port 8000). The AI sidecar is a separate Node 22 / TypeScript process (Fastify, port 4317). They share no code and never call each other over HTTP. Their only contract is the filesystem: the pipeline writes run outputs under data/runs/{run_id}/; the sidecar reads them as opaque evidence and writes only into each run's ai_insights/ subtree.

The defining choice — visible in the health endpoint's self-description "single_pi_sidecar" (ai-sidecar/src/server.ts:71) — is that each conversation owns one long-lived Pi AgentSession, cached in memory by conversationId (ai-sidecar/src/runtime.ts:75). "Standard" and "Deep Research" are not different engines; they are policy labels that only widen the grounding byte budget (100 KB → 180 KB, ai-sidecar/src/runtime.ts:158).

2 · Pi in a nutshell — and how the sidecar builds a session

Pi ships three layered packages, all pinned to 0.79.9 (ai-sidecar/package.json:17):

PackageLayerWhat it provides
@earendil-works/pi-aiModel / providerThe Model<Api> abstraction and provider stream functions (Anthropic, OpenAI-completions, Google, Bedrock, …). Pure model I/O.
@earendil-works/pi-agent-coreAgent loopThe Agent class and the agentic loop (agent-loop.js): model call → tool execution → repeat. Tools, events, usage.
@earendil-works/pi-coding-agentHarness / SDKAgentSession, the built-in coding tools (read/bash/edit/write/…), skills, extensions, sessions, the createAgentSession() SDK factory.

The sidecar uses the SDK exactly as documented in Pi's docs/sdk.md. The whole construction lives in one method, PiRuntime.sessionFor() (ai-sidecar/src/runtime.ts:221), invoked lazily the first time a conversation sends a turn:

// ai-sidecar/src/runtime.ts:221 — abbreviated
const key = this.keyResolver(request.userId, model.provider);   // BYOK sqlite → env
const authStorage = AuthStorage.create();
authStorage.setRuntimeApiKey(model.provider, key);              // in-memory, never persisted
const registry = ModelRegistry.create(authStorage);

const aiRoot  = this.runs.aiRoot(request.runId);                // data/runs/{id}/ai_insights
const cwd     = path.join(aiRoot, "work", request.conversationId);
const sessions = path.join(aiRoot, "sessions");

const resourceLoader = new DefaultResourceLoader({ cwd, agentDir: getAgentDir() });
await resourceLoader.reload();
const skillResources = resourceLoader.getSkills();             // { skills, diagnostics }

const sessionManager = SessionManager.create(cwd, sessions);
const created = await createAgentSession({
  cwd, model: toPiModel(model), authStorage, modelRegistry: registry,
  sessionManager, resourceLoader, tools: [],                    // ← the load-bearing empty array
});

Each SDK object has a single job. AuthStorage resolves provider credentials; setRuntimeApiKey() injects the resolved key in memory only, so it never lands in auth.json, sessions, or child-process env (docs/sdk.md "API Keys and OAuth"). ModelRegistry knows which models exist. DefaultResourceLoader discovers extensions, skills, prompts, and context files from cwd and agentDir; the sidecar calls getSkills() purely to count and name what Pi found. SessionManager persists the conversation tree as JSONL under ai_insights/sessions. createAgentSession() wires them together and returns an AgentSession.

The load-bearing detail

tools: [] is not a placeholder — it is the single most consequential line in the file. In Pi, tools is an allowlist of built-in tool names; the defaults are ["read", "bash", "edit", "write"] (pi-coding-agent docs/sdk.md:472). Passing an empty array enables none of them, and the sidecar registers no custom tools either. The model can therefore think and write prose, but it cannot read a file, run a command, or edit code. Hold onto this; §4–§9 all turn on it.

3 · The AgentSession interface (and the sidecar's seam over it)

Once built, the session is the entire surface the sidecar drives. It uses six members of it, and nothing else:

The sidecar does not let the rest of the app see AgentSession directly. It hides Pi behind its own narrow Runtime interface (ai-sidecar/src/runtime.ts:54) — a four-method seam that returns an async stream of the sidecar's own RuntimeFrame type:

// ai-sidecar/src/runtime.ts:54

This seam is deliberate. buildServer() accepts a runtime override (ai-sidecar/src/server.ts:45), so the entire test suite injects a fake Runtime and exercises the HTTP/SSE layer with no provider, no key, and no network. PiRuntime is the only production implementation; swapping engines means writing a second one, not editing the server.

4 · The agentic loop — the heart of Pi

This is the concept everything else hangs on. When you call session.prompt(), Pi does not make one model call and return. It runs a loop. The model replies; if its reply contains tool-use blocks, Pi executes those tools, appends the results to the conversation, and calls the model again with the results in context. It repeats until the model answers with no tool calls. That loop is what makes an LLM an agent.

The loop lives in pi-agent-core/dist/agent-loop.js in a function runLoop() (agent-loop.js:77). Its shape — verified against the compiled source:

The inner loop continues while (hasMoreToolCalls || pendingMessages.length > 0) (agent-loop.js:87). After each assistant message Pi filters for tool-call blocks; hasMoreToolCalls is set to false when there are none (agent-loop.js:115), which is the normal way a turn ends. Tool batches can also signal early termination: a result may set terminate: true, and when every result in a batch does, the loop stops (shouldTerminateToolBatch, agent-loop.js:296). An outer while (true) (agent-loop.js:84) then checks for queued follow-up messages (getFollowUpMessages, agent-loop.js:157) before truly finishing with agent_end.

Gotcha: Pi has no native max-rounds cap

The sidecar's .env advertises AI_PI_MAX_TOOL_ROUNDS=8, but pi-agent-core enforces no iteration counter — the loop terminates only on "no tool calls", a terminate batch, an error/abort, or a shouldStopAfterTurn callback. Any round cap is the embedder's job. The sidecar's actual backstop is different and blunter: a 180-second wall-clock timeout wrapped around the whole frame stream (withTurnTimeout, ai-sidecar/src/server.ts:391; AI_PI_TURN_TIMEOUT_SECONDS, ai-sidecar/src/config.ts:74). The MAX_TOOL_ROUNDS var is currently inert — it is declared in .env but never read by the sidecar or passed to Pi.

Tool calls within one batch run in parallel by default; a tool may opt into executionMode: "sequential", and if any tool in the batch is sequential the whole batch serialises (executeToolCalls, agent-loop.js). Each tool is looked up by name in context.tools; an unknown name yields an immediate error result rather than throwing. Two interception hooks bracket every call — beforeToolCall (which an extension can use to block, e.g. confirm before rm -rf) and afterToolCall — installed by the session at pi-coding-agent dist/core/agent-session.js:186.

5 · How code gets generated

"The agent wrote code" is, mechanically, just the model calling the write or edit tool with code in the arguments. There is no special code-generation path — code is generated the same way any tool argument is, then a filesystem write makes it real.

The write tool — create or overwrite a file

Its parameter schema is two strings (pi-coding-agent dist/core/tools/write.d.ts:4):

writeSchema = Type.Object({
  path:    Type.String(),   // file to create/overwrite
  content: Type.String(),   // full file contents — the generated code
})

On execute it creates parent directories recursively and writes the file UTF-8. The model "generates a script" by emitting a write call whose content is the script.

The edit tool — surgical patches

The edit tool takes a path plus an array of { oldText, newText } replacements (pi-coding-agent dist/core/tools/edit.d.ts:10). Crucially for an embedder, it returns both a human diff and a machine patch in its details (edit.d.ts:18):

interface EditToolDetails {
  diff:  string;              // display-oriented, for a TUI
  patch: string;              // standard unified patch, for SDK consumers
  firstChangedLine?: number;  // for editor navigation
}

An SDK integration like the sidecar would read details.patch to show or apply changes. The bundle of these is what Pi calls the coding tool set: createCodingTools(cwd) returns exactly [read, bash, edit, write] (pi-coding-agent dist/core/tools/index.js:85) — the four defaults. createReadOnlyTools() swaps in [read, grep, find, ls] for a no-write agent.

In the sidecar

With tools: [], neither write nor edit is registered, so the model cannot generate files at all today. Generated answers are prose streamed back as text; no artifact is produced by the model. (Researcher uploads are a different path — see §9.)

6 · How Python actually runs

Pi has no dedicated "Python tool". Python runs the way everything else runs: the model calls the bash tool with a command like python3 analysis.py, and Pi spawns a shell. Understanding the bash executor is understanding how Python runs.

The executor is pi-coding-agent dist/core/tools/bash.js. The spawn is a plain Node child_process.spawn of the configured shell (bash.js:39):

// pi-coding-agent dist/core/tools/bash.js:39
const child = spawn(
  shellConfig.shell,
  commandFromStdin ? shellConfig.args : [...shellConfig.args, command],
  { cwd, detached: process.platform !== "win32",
    env: env ?? getShellEnv(),
    stdio: [commandFromStdin ? "pipe" : "ignore", "pipe", "pipe"],
    windowsHide: true },
);

Four properties matter when you reason about a Python step:

  • Fresh shell per command. Each bash call spawns a new process — there is no persistent shell, so cd or an env var set in one call does not carry to the next. State must live on disk or in the command itself.
  • Working directory = the agent's cwd. For the sidecar that is data/runs/{id}/ai_insights/work/{conversationId} (ai-sidecar/src/runtime.ts:230). So python3 analysis.py resolves relative to that scratch dir, and any file the model wrote there with write is runnable.
  • No default timeout. The tool's own description says so: output is truncated but "no default timeout" unless the model passes a timeout in seconds (bash.js:194). On timeout or abort the whole process tree is killed via killProcessTree, so a Python subprocess can't be orphaned.
  • Output is bounded. stdout+stderr are merged, ANSI-stripped, and truncated to the last 2000 lines or 50 KB, whichever hits first (DEFAULT_MAX_LINES / DEFAULT_MAX_BYTES, pi-coding-agent dist/core/tools/truncate.js:10). If truncated, the full output is saved to a temp file and its path returned, so a chatty script degrades gracefully instead of flooding context.
In the sidecar

This is now wired (§9): under the developer gate the session registers bash, so the model runs python3 against files in the scratch cwd. The AI_PYTHON_EXECUTION=developer-local setting (ai-sidecar/src/config.ts:49) is the switch — set it to disabled, or turn off AI_DEVELOPER_MODE, and the session falls back to tools: [] with no shell and no Python.

7 · How skills get pulled in

A skill is a self-contained capability package the agent loads on demand: a directory with a SKILL.md (frontmatter + instructions) plus optional helper scripts, references, and assets. Pi implements the Agent Skills standard. The mechanism is progressive disclosure, and it is elegant precisely because it is cheap.

The lifecycle

  1. Scan — at startup Pi scans skill locations and extracts each skill's name + description from SKILL.md frontmatter (pi-coding-agent docs/skills.md:66). Locations include global ~/.pi/agent/skills/ and ~/.agents/skills/, project .pi/skills/ and .agents/skills/ (after the project is trusted), package skills/ dirs, and explicit settings/CLI paths (docs/skills.md:24).
  2. Advertise — the system prompt lists available skills in XML, descriptions only. This is the whole of progressive disclosure: descriptions are always in context; full instructions are not (docs/skills.md:71).
  3. Load on match — when a task matches, the model uses the read tool to open the full SKILL.md. (Models don't always do this reliably, so Pi also exposes a /skill:name command to force it — docs/skills.md:68.)
  4. Execute — the model follows the instructions, invoking the skill's bundled scripts via bash using paths relative to the skill directory.

The SKILL.md contract

Frontmatter requires just name and description; optional fields include allowed-tools (a pre-approved tool list, experimental) and disable-model-invocation (hide from the prompt; only reachable via /skill:name). A minimal example:

---
name: brave-search
description: Web search and content extraction via Brave Search API. Use for
  searching documentation, facts, or any web content.
---

# Brave Search
## Setup
```bash
cd /path/to/brave-search && npm install
```
## Search
```bash
./search.js "query" --content
```

What the sidecar sees

The DefaultResourceLoader.getSkills() call returns a { skills, diagnostics } result whose Skill shape is (pi-coding-agent dist/core/skills.d.ts:9):

interface Skill {
  name: string;
  description: string;
  filePath: string;
  baseDir: string;
  sourceInfo: SourceInfo;           // where it was discovered
  disableModelInvocation: boolean;
}

The sidecar reads skills[].name and the count of diagnostics (validation warnings), stashing them as discoveredSkills / skillDiagnostics for the operations dashboard (ai-sidecar/src/runtime.ts), and — when the execution gate is open — injects the committed catalog into the session so the model can actually load and run them (§9).

8 · The event bridge — Pi events → SSE

Everything the sidecar shows the user is reconstructed from Pi's event stream. session.subscribe() delivers a discriminated union, AgentSessionEvent (pi-coding-agent dist/core/agent-session.d.ts:40), which extends the core AgentEvent union (pi-agent-core dist/types.d.ts:359). 9 · Execution — skills & Python are now live (developer-gated)

§6 and §7 described capabilities that ride on tools (bash to execute, read to open a SKILL.md). Those tools are now registered — but only behind a hard gate. PiRuntime computes executionEnabled = developerMode && pythonExecution !== "disabled" in its constructor (ai-sidecar/src/runtime.ts). Production, or any build with AI_PYTHON_EXECUTION=disabled, still creates the session with tools: [] and injects no skills. When the gate is open the session is created with a deliberate allowlist plus one custom tool:

// ai-sidecar/src/runtime.ts — sessionFor()
tools: ["read", "bash", "write", "edit", "save_artifact"],
customTools,   // defineTool({ name: "save_artifact", … })
  • read opens a skill's SKILL.md. Pi advertises its absolute path as the <location> in the system prompt, so the model can read it even though the bash cwd is the ephemeral per-conversation work dir.
  • bash runs bundled skill scripts and python3.
  • write/edit generate code into the work dir.
  • save_artifact copies a file the skill produced into the run's ai_insights/artifacts/ and registers it via store.addArtifact, so it appears in GET /api/artifacts — a bash write into that directory alone would not register it.

Skills are committed under ai-sidecar/skills/ and injected into every session through DefaultResourceLoader's skillsOverride (built with the exported loadSkillsFromDir()), independent of the ephemeral cwd. Four deterministic validation skills ship today — sf-runtime-probe, sf-echo-script, sf-python-compute, sf-artifact-report — each emitting a unique greppable sentinel and exercised by the opt-in live smoke (npm run test:live-skills).

Because diagnostics().registeredTools and the session_created payload now report the real tool names, both operations-center warnings clear and capabilities.pythonExecutable becomes true. executionCategory() (runtime.ts) labels each call deterministically — a python3 shell command → python; a SKILL.md read or a command under skills/ → skill; write/edit/save_artifact → tool — so the per-turn trace counts toolRuns/skillRuns/pythonRuns unambiguously and ADVERTISED_SKILLS now mirrors the committed skills.

Trust model & isolation

Execution is developer-local: gated to AI_DEVELOPER_MODE, it trusts the local developer and is not OS-sandboxed. The bash cwd is the conversation work dir and every output delta is still scrubbed (runtime.ts scrubOutput), but absolute-path reads/writes are not blocked — that is required for the skill-load flow and accepted under the developer gate. Pi's process-isolation patterns (Gondolin micro-VM, Docker, OpenShell — §10) remain the backlog for untrusted or multi-tenant execution. AI_PI_MAX_TOOL_ROUNDS is still inert (Pi exposes no native round cap); the AI_PI_TURN_TIMEOUT_SECONDS deadline is the enforced bound on a multi-round turn. The off-limits rule stands: pipeline-owned Python (pipeline.py, stage runners, r_scripts/) is never driven by the AI.

10 · Security & isolation boundary

Because the sidecar embeds an agent that could (once tools are on) run arbitrary code, isolation is layered at the boundary rather than trusted to the model:

  • Input gate. inspectPrompt() (ai-sidecar/src/security.ts:9) regex-blocks extraction attempts ("reveal the system prompt", "api key", …) before a turn ever reaches Pi.
  • Output scrub. Every text_delta is passed through scrubOutput() inside the runtime (ai-sidecar/src/runtime.ts:121) before leaving — redacting key shapes and absolute home paths. Operational trace payloads get a deeper recursive scrub (scrubOperationalValue).
  • Key handling. BYOK keys are AES-256-GCM encrypted with a key derived from SESSION_SECRET (ai-sidecar/src/crypto.ts:5), never returned by any endpoint, and injected only via setRuntimeApiKey() (in-memory).
  • Transport headers. Every response carries Content-Security-Policy: default-src 'self', X-Content-Type-Options: nosniff, and Referrer-Policy: no-referrer (ai-sidecar/src/server.ts:64).
  • Filesystem confinement. The run catalog hides ai_insights/ and R internals from grounding (visibleFile, ai-sidecar/src/run-catalog.ts:22), and every artifact path is validated against traversal (ai-sidecar/src/store.ts:183, server.ts:367).

Pi adds its own seams: the beforeToolCall extension hook (agent-session.js:186) can block a command pre-execution, and Pi documents three process-isolation patterns — a Gondolin micro-VM, plain Docker, or NVIDIA OpenShell — for routing tool execution into a sandbox (pi-coding-agent docs/containerization.md). None is wired into the sidecar yet: now that tools execute (§9), confinement rests on the developer-mode gate and the work-dir cwd rather than an OS sandbox — adopting one of these patterns is the path to untrusted or multi-tenant execution.

12 · Key design decisions

  1. Embed Pi instead of building an LLM loop established 2026-06

    Rather than hand-roll streaming, tool-use, sessions, and skills, the sidecar embeds Pi's SDK and supplies only model, key, cwd, and grounding. The cost is a heavy dependency and Pi's release cadence (pinned to 0.79.9); the benefit is that the entire agentic loop, event model, and tool framework are maintained upstream. The sidecar's job shrinks to grounding + persistence + a safety boundary.

  2. One persistent AgentSession per conversation established 2026-06

    Sessions are cached in a Map keyed by conversationId (runtime.ts:75) and reused across turns, so model context, history, and any future tool state stay warm. "Standard" vs "Deep Research" are policy profiles over the same session, differing only in grounding budget — not separate runtimes. dispose() on delete/clear is the explicit lifecycle end.

  3. Tools off in production, on behind the developer gate established 2026-06

    The v1 default of tools: [] (grounded Q&A, zero code-execution risk) is preserved for production: tools and skills register only when AI_DEVELOPER_MODE=1 and AI_PYTHON_EXECUTION ≠ disabled. The scaffolding that was always pre-wired — executionCategory(), the AI_PYTHON_EXECUTION config, the operations warnings — now lights up when the gate is open: read/bash/write/edit/save_artifact register, the committed skills inject, and the dashboard's configured-Python / advertised-skills / Pi-discovered-skills / registered-tools / observed-executions columns converge instead of warning. The gap is closed under the gate and stays visible (and locked) without it.

  4. A narrow Runtime seam over Pi established 2026-06

    The server depends on a four-method Runtime interface returning the sidecar's own RuntimeFrame, not on AgentSession directly (runtime.ts:54). This lets the HTTP/SSE suite inject a fake runtime with no provider or network, and isolates the (fast-moving) Pi API behind one file. Swapping engines means writing a second Runtime, not editing routes.

  5. Security at the boundary, not in the model established 2026-06

    Extraction blocking, output scrubbing, key encryption, CSP headers, and filesystem traversal checks live in the sidecar's own code, independent of model behavior. The model is never trusted to keep a secret; the runtime scrubs deltas before they leave (runtime.ts:121). This holds even if a future model or a malicious grounding file tries to exfiltrate.

15 · Glossary

AgentSession
Pi's per-conversation object: owns message history, model, compaction, and the event stream. The sidecar caches one per conversationId.
Agentic loop
Pi's core control flow: call model → execute the tools it requested → append results → call model again, until the model emits no tool calls (agent-loop.js).
BYOK
"Bring your own key" — a provider API key the user pastes into the UI; stored AES-256-GCM encrypted, injected at runtime, never returned.
createAgentSession()
The Pi SDK factory that wires auth, models, resources, and session storage into an AgentSession.
defineTool()
Pi helper that defines a custom tool (name, description, TypeBox params, execute) the model can call. A type-preserving pass-through.
DefaultResourceLoader
Pi's discoverer of extensions, skills, prompts, themes, and context files from cwd and agentDir.
Grounding
The run-evidence excerpt the sidecar selects (up to 12 files within a byte budget) and prepends to the prompt as primary evidence (run-catalog.ts:80).
Pi
The embeddable coding-agent harness (@earendil-works/pi-*) this sidecar is built on. Provides the loop, tools, skills, and event model.
Progressive disclosure
Skill loading strategy: only descriptions sit in the system prompt; full SKILL.md instructions load on demand via the read tool.
RuntimeFrame
The sidecar's own event type, translated from Pi's AgentSessionEvent and serialised to the browser as SSE.
Skill
A self-contained capability package (SKILL.md + scripts/assets) the agent loads on demand, per the Agent Skills standard.
Sidecar
The standalone Node/Fastify service (ai-sidecar/, port 4317) that hosts AI Insights, separate from the FastAPI pipeline.
tools: []
The empty allowlist the sidecar passes to createAgentSession() — enables no built-in tools, so the model can answer but not execute code today.
