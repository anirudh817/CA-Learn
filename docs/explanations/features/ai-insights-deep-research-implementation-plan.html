1. The decision in one page

Recommendation. Implement Deep Research as a durable research-job layer over the existing Pi sidecar. First extract the latest adaptive/BM25 Standard grounding into a shared service. Then add approved, manifest-driven skills and curated external lookups. Every result card must say what SignalFold processed, what a new computation added, and what external research supports or challenges—without blending those into one opaque answer.

What the user does

Selects a completed run, chooses a concrete investigation, answers at most two useful clarifiers, reviews scope/cost/skills, and approves a plan. The job continues independently of the open chat.

What SignalFold does

Freezes a run-evidence manifest from the same grounding index as Standard Mode; executes only allow-listed skills against explicit inputs; performs bounded external corroboration; records every transformation and source.

What the user receives

A decision-first result containing eight durable outputs: summary, HTML report, evidence record, artifacts, computation manifest, re-run action, open questions, and recommended next step.

Product boundary. This mode produces auditable analysis and research hypotheses. It does not claim causal mechanism, clinical validation, biological novelty, or experimental confirmation. A job that performs no new computation, finds no new corroboration, and surfaces no contradiction must be labeled Standard-equivalent.

2. New-session bootstrap: start here

This section is intentionally operational. A fresh implementation session should perform these steps before changing the UI or importing skills.

  1. Verify branch ssb1 and preserve unrelated worktree changes. Do not create a feature branch unless explicitly requested.
  2. Read this document, the brainstorm, docs/explanations/the-science-of-signalfold.html, and docs/scientific-agents-profiles.html.
  3. Confirm the latest grounding baseline in ai-sidecar/src/standard-grounding.ts:192-285: deterministic run card, artifact-family routing, bounded evidence selection, row identifiers, and BM25 lexical fallback. The current checkpoint is commit 9c4ea5a, followed by explanatory commit fbc1160.
  4. Confirm the current Deep Research fork in ai-sidecar/src/runtime.ts:237-285. Standard uses buildStandardGrounding; Deep Research still uses groundingSnapshot(..., 180_000). Replace this split before building research cards.
  5. Write characterization tests that freeze Standard grounding behavior. Refactor to a policy-neutral index/retrieval service; do not rewrite or regress Standard Mode.
  6. Implement a frozen ResearchScopeManifest using that shared service: selected artifacts, row IDs, stage configuration, file hashes, exclusions, budget, query/plan, and creation time.
  7. Only after the grounding tests pass, add the job schema, plan approval, skill runner, and UI in the phases below.
Do not start by wiring all 17 skills. The first risk is not missing Python; it is producing plausible cards that silently ignore how SignalFold generated the selected run. Phase 0 makes that impossible by contract.

The moat is not generic browsing. General LLM research products can search papers. They do not possess the user’s immutable SignalFold run, its normalization and threshold choices, feature/module/pathway/cell-type tables, or a re-runnable computation manifest bound to those exact files. The differentiated object is therefore:

Private run evidence + pipeline-aware interpretation + reproducible computation + curated external corroboration + claim-level provenance.

4. End-to-end user workflow

  1. Enter Deep Research. In AI Insights, the mode switch changes the central surface from a chat stream to a research workspace. The currently selected completed run is always visible.
  2. Choose an entry point. Use one of six workflow cards or type a question. Cards are opinionated templates, not canned reports.
  3. Preflight. SignalFold checks required artifacts, sample/group sufficiency, skill availability, external credentials, network policy, estimated compute, and spend cap.
  4. Clarify only what changes the plan. Ask at most two inline questions, such as the focal module/protein or whether alternative thresholds are acceptable. Infer everything else from the run.
  5. Review a concrete plan. Show objective, exact run inputs, steps, skills, external sources, output types, estimated time/cost, and known limitations. Let the user edit the objective, scope, thresholds, sources, or budget.
  6. Approve. Approval freezes ResearchScopeManifest, model, source policy, skill versions, and spending ceiling. No networked or computational work begins before this.
  7. Observe or leave. The stepper reports grounding, computation, corroboration, synthesis, packaging, and costs. The user may pause, resume, or stop; closing the view does not abort the job.
  8. Review findings. Result cards lead with decisions and contradictions, not a long essay. Each card expands into pipeline rows, computation records, and external sources.
  9. Act. Re-run the full plan, fork it with changed parameters, open an artifact, export the HTML research package, or start the recommended next investigation.

6. Six launch workflows and tangible outcomes

1 · Finding Stress Test

User asks: “Does this protein/module/cell-type result survive reasonable analytical choices?”

Work: threshold sweep, leave-one-sample-out influence, alternative multiple-testing cutoffs, distribution/assumption checks.

Skills: statsmodels, statistical-power, exploratory-data-analysis, matplotlib.

Outcome: stable, threshold-sensitive, sample-driven, or insufficient—with sensitivity table and plot.

2 · Ranked Pathway Investigation

User asks: “What biology appears across the full ranked signal, beyond the arbitrary hit cutoff?”

Work: start from Stage 1’s processed ranking; compare SignalFold module ORA with a seeded preranked enrichment path; inspect leading-edge genes.

Skills: pathway-enrichment, gget, scientific-visualization.

Outcome: convergent and divergent pathways, with an explicit warning that the new ranked analysis is not the same method as Stage 2 FET.

3 · Module Hub Investigation

User asks: “Which members actually organize this module, and is the hub story credible?”

Work: use Stage 1 module assignments/kME and network edges; compare membership, centrality, effect size, and external protein/pathway evidence.

Skills: networkx, bioservices, gget, citation-management.

Outcome: hub candidates ranked by separate network and biological dimensions—not a single magical score.

4 · External Protein Evidence

User asks: “What is known about my top proteins in this disease/tissue/context?”

Work: bind UniProt/Reactome/KEGG/PubMed evidence to exact Stage 1 rows; map identifiers; record support, contradiction, or no information.

Skills: gget, bioservices, database-lookup, citation-management.

Outcome: per-protein evidence cards whose first line is the SignalFold observation, not a generic protein biography.

5 · Run vs Literature Contradiction Check

User asks: “Where does this run disagree with published expectations?”

Work: extract directional run claims; search targeted sources; test claim entailment; distinguish tissue/model/cohort differences from genuine conflict.

Skills: citation-management, database-lookup, markitdown/liteparse for user papers.

Outcome: a contradiction register with plausible explanations and experiments—not forced consensus.

6 · Power and Next Experiment

User asks: “What follow-up study would most efficiently resolve this uncertainty?”

Work: derive effect/variance assumptions from the processed run, calculate or simulate sample size/MDE, propose balanced/randomized designs, expose assumptions.

Skills: statistical-power, experimental-design, statsmodels.

Outcome: decision table across feasible sample sizes plus a design file; never presented as a guaranteed validation plan.

Later, not v1: whole-run publication brief, cross-run investigation graph, autonomous multi-agent fan-out, raw LC-MS reprocessing, and single-cell reanalysis. They are valid extensions, but they dilute the fastest proof of value.

7. The eight required deliverables

A completed job is invalid until all eight slots exist. “Not applicable” is allowed only with a recorded reason.

1Decision summary

Three to seven sentences: answer, strongest evidence, most important caveat, and decision implication.

2Research report

Self-contained HTML narrative linking every material claim to its evidence card and artifacts.

3Evidence record

Machine-readable claims and edges across pipeline, computation, and external evidence.

4Generated artifacts

Tables, figures, code/notebooks, parsed attachments, and intermediate outputs worth inspecting.

5Computation manifest

Skill/source commit, script, environment, inputs, params, seeds, outputs, hashes, exit, runtime, and cost.

6Re-run action

Repeat exactly, or fork with editable parameters; show which external facts may have changed.

7Open questions

Unresolved evidence gaps, contradictions, missing metadata, and questions requiring domain review.

8Recommended next step

One prioritized action with expected information gain, effort/cost, and stopping rule.

8. Research cards: dual grounding is a hard rule

Cards are not summaries produced from model memory. They are rendered views of a structured claim object. Every run-specific finding begins from what SignalFold actually processed; external research is attached only to the interpretive portion.

Example: “Turquoise-module microglia interpretation is supported, but sensitivity remains uncertain”interpretation · medium

Decision implication. Treat the signal as a prioritized hypothesis, not validation; run leave-one-out stability before selecting APOE as the follow-up target.

Pipeline evidence
Stage 1 module/kME rows + Stage 3 microglia FDR rows; exact configs; file/row IDs and SHA-256.
New computation
Optional influence/sensitivity skill; parameters, seed, environment, outputs and reproducibility result.
External evidence
Targeted sources supporting, challenging, or contextualizing the interpretation; PMID/accession and retrieval date.

Limitations. Module membership reflects co-variation; cell-type FET depends on the chosen marker reference and tested universe; the current run does not establish causality.

Claim types and required evidence

Claim typeExampleRequired arm(s)Permitted language
observation“Feature X has log2FC 1.1 and BH-adjusted p 0.03.”Pipeline, exact row + processing config.“SignalFold reported…”
computation“The finding remains significant in 7/8 leave-one-out fits.”Pipeline + computation.“The approved sensitivity analysis found…”
interpretation“The module is consistent with a microglial process.”Pipeline + external; computation when analysis adds support.“Consistent with,” “supports,” “suggests.”
hypothesis“APOE may organize a disease-relevant response.”At least pipeline + external, with explicit gaps.“Hypothesis,” “candidate,” “requires validation.”

Four evidence dimensions—never one synthetic truth score

Pipeline support

Directness and completeness of the underlying SignalFold rows/configs.

Analytical robustness

Threshold, sample, method, and assumption sensitivity; not run is different from weak.

External consistency

Support, conflict, mixed, context-dependent, or no information.

Replication status

Single run, internal split, independent cohort, or experimentally validated. Default is single run.

Use plain verdict tags such as stable, threshold-sensitive, sample-driven, context-dependent, and insufficient evidence. Avoid medical GRADE labels; they imply an evidence hierarchy the product has not established.

9. Ready-to-implement card-generation prompt

The following belongs in the stable Deep Research synthesis policy, backed by schema validation. It explicitly enforces the user’s requirement that cards reflect good research and SignalFold pipeline processing.

You are the SignalFold Deep Research synthesis writer.

PRIMARY RULE
Every run-specific claim must be grounded first in the selected SignalFold run and in
the exact processing that produced it. Do not write a generic scientific interpretation
when SignalFold pipeline evidence exists. External research may contextualize, support,
or challenge a pipeline-derived claim; it must never overwrite or silently replace the
run result.

FOR EACH FINDING CARD
1. Reconstruct the SignalFold fact:
   - cite artifact path and row/cell identifiers;
   - cite the stage configuration and relevant processing method;
   - preserve the actual comparison direction, scale, thresholds, background universe,
     multiple-testing scope, module/reference choice, and missing-data behavior;
   - include the immutable file hash from ResearchScopeManifest.
2. If a new computation was run, describe it separately:
   - skill, implementation kind, source revision, provider, script/operation, environment, inputs and hashes;
   - parameters, random seed, outputs and hashes, exit status, runtime and cost;
   - whether an exact re-execution check passed.
3. For biological interpretation, perform targeted external research:
   - cite stable identifiers (PMID/DOI/accession), retrieval date, and source snapshot;
   - classify each source as supports, challenges, contextualizes, or no information;
   - ensure the cited passage actually entails the written claim;
   - surface contradictions and context differences rather than forcing agreement.
4. Label the card observation, computation, interpretation, or hypothesis.
5. Report pipeline support, analytical robustness, external consistency, and replication
   status as separate dimensions. Never collapse them into one confidence score.
6. State limitations and a decision implication.

SIGNALFOLD-SPECIFIC GUARDRAILS
- Stage 1 values come from SignalFold's normalized data and configured Welch t-test or
  Wilcoxon path, followed by the configured p-value adjustment and fold-change cutoff.
  Do not describe these results as limma, DESeq2, causal effects, or validated biomarkers.
- WGCNA modules describe co-variation and are sensitive to sample count, feature filtering,
  soft power, correlation/network type, module size, tree cut, merge, and grey assignment.
- Stage 2 uses module over-representation/Fisher exact testing against its configured
  universe (measured features by default), global BH FDR, a signed FET-derived z score,
  and optional kappa redundancy removal. Do not call it GSEA unless a separate approved
  GSEA computation was actually run and clearly labeled as a new method.
- Stage 3 uses one-sided Fisher exact tests over module genes and the configured cell-marker
  reference, with BH adjustment within each module. Cell-type enrichment is not measured
  cell abundance and may reflect marker/reference or tissue mismatch.
- Missing values are filtered/ignored according to the run configuration; they are not
  automatically modeled as biological absence.
- Association is not causation; discovery is not validation; novelty requires a targeted
  precedent search and human review.

OUTPUT CONTRACT
Return schema-valid finding cards only. If any material statement lacks the required arm,
mark it unsupported and move it to Open Questions. If no new computation, corroboration,
or contradiction was produced, mark the job Standard-equivalent.

run_skill receives only jobId, stepId, skillId, entrypoint, manifest-selected inputs, and validated parameters. 14. Security, trust, and reproducibility boundaries

  • Read-only run inputs. Skills receive copied or mounted immutable artifacts selected by the manifest. They never modify Stage 1–3 outputs.
  • Review-gated, repository-owned catalog. No cloning, installing, or updating third-party skills during a user turn. Imported implementations enter the repository only after license/security review and fixture tests; native SignalFold skills pass the same manifest and quality gates.
  • Structured capabilities. Product jobs expose run_skill, curated lookup tools, read-scoped evidence access, and artifact registration—not generic bash/write/edit. Developer mode may retain generic tools outside the supported product path.
  • Network tiers. Offline skills first. Networked skills use domain allow-lists, cache, quotas, timeout/circuit breaker, response-size limits, source snapshots, and secrets kept outside prompts/logs.
  • Untrusted external content. Retrieved papers/pages and parsed attachments are evidence, never instructions. Quarantine them from system/skill policies.
  • Content addressing. Hash inputs, outputs, source snapshots, plan, manifest, and report. Record tool/library versions and environment/image digest.
  • Single-user first. The present developer-local executor is acceptable for proving value on the owner’s machine. Multi-user release is blocked on process/container isolation, quotas, tenant boundaries, and abuse tests.

The provenance shape should map naturally to W3C PROV’s Entity–Activity–Agent model, while the exported package can later adopt an RO-Crate profile for data, workflows, scripts, provenance, and a human-readable HTML preview.

15. Detailed implementation sequence and exit gates

Phase 0 · Share the latest grounding substrate must be first

  • Add characterization tests for Standard keyword routes, explicit lookups, BM25 fallback, citation rows, token budgets, and no-evidence definitional questions.
  • Extract artifact indexing, run-card construction, classification/ranking, row selection and citations into policy-neutral modules.
  • Keep buildStandardGrounding as a compatibility facade.
  • Add buildResearchScopeManifest(runId, question, plan) with config discovery, hashes, exclusions, and immutable artifact/row refs.
  • Switch Deep Research away from groundingSnapshot; retain broad snapshot only as a deprecated fallback until tests prove parity, then remove it from active policy.

Exit: all existing Standard grounding tests are unchanged/passing; Deep Research test proves it selects relevant evidence and exact configs instead of the first 180 KB.

Phase 1 · Job skeleton and plan approval
