SignalFold AI Insights Standard mode: adaptive grounding design

Status: implemented on ssb1

Current implementation: ai-sidecar/src/standard-grounding.ts, ai-sidecar/src/runtime.ts, and ai-sidecar/src/server.ts

Scope: Standard mode only. Deep Research behavior is not implemented by this change; its policy seam remains available.

Update (2026-06-22) — what changed: the deferred relevance-retrieval layer (#3) is now implemented. Full detail in §4 “Relevance fallback for unmatched data questions”; the one-paragraph version:

Before. Question routing was keyword-only. A data question worded outside the enumerated keyword/entity lists fell through to the general route and grounded zero run files — even though the data to answer it existed in the run. Adding more synonyms never generalised; the next paraphrase failed the same way. Confirmed example: “Which proteins rise and fall in lockstep across samples?” grounded nothing.

After. The keyword fast-path is unchanged, but when it would return general on a non-definitional question, a deterministic Okapi BM25 pass ranks the run's own artifacts and grounds the best-matching evidence families through the existing retrieval path. These turns report a new lexical route.

Unchanged, and the cost. Same run card, same retrieval/scoring/budget/citation path, and the same zero grounding for definitional, product/help, and off-topic questions. Still zero extra model calls — no embeddings, no persistent index. The change is one file, ai-sidecar/src/standard-grounding.ts (+203 lines); runtime.ts and server.ts are untouched because the route value passes straight through.

1. Outcome

Standard mode now uses a deterministic, relevance-gated grounding path inside the canonical Node/Pi sidecar. A turn always receives a compact run card, but it receives run-file rows only when the question calls for them. The same Pi runtime still owns sessions, model switching, streaming, persistence, cancellation, output scrubbing, usage, and cost attribution.

Standard is deliberately not a coding agent. Even when developer execution is enabled, a Standard session receives no Pi skills and no read, Bash, Python, write, edit, or arbitrary filesystem capabilities. Retrieval happens on the server before the model call through path-confined, schema-bounded code.

2. Request flow

POST /api/conversations/:id/turns
  -> security inspection
  -> durable user-message write
  -> attachment resolution and untrusted-data wrapping
  -> PiRuntime.turn()
     -> select policy-specific Pi capabilities
     -> build compact deterministic run card
     -> classify the question with deterministic heuristics
     -> index candidate artifacts by schema
     -> retrieve, score, rerank, and budget evidence
     -> compact durable history when restoring a cold session
     -> compose stable-to-dynamic prompt
     -> stream through the shared Pi session
     -> record per-call and cumulative usage
  -> persist answer, citations, provenance, trace, and cost

There is no Python chat fallback and no second Standard backend.

3. Compact deterministic run card

buildRunCard() produces orientation metadata, not an LLM-written summary. It contains:

  • run ID and COMPLETE status;
  • format family, assay/input level, sample count, and feature count when present;
  • available stage names and stage configuration-file availability;
  • artifact families, representative relative paths, important columns, bounded row counts, byte availability, and family counts;
  • explicit nulls for unavailable quality-control and missing-data fields.

The card does not select permanent “top findings.” On RUN-E2E-VERIFY it is approximately 2,128 tokens, within the initial 1–3k-token hypothesis.

The artifact index is cached by completed-run index signature. Complete runs are treated as immutable; a changed artifact_index.json invalidates the cache.

4. Deterministic query routing

classifyStandardQuery() uses explainable keyword and entity rules. It adds no model call.

Route Examples Run-file body
general “What does FDR mean?”, product/help questions 0 tokens
lexical data question phrased outside the keyword lists (“What are the biggest abundance changes between conditions?”) — resolved by the BM25 relevance fallback relevance-selected rows
lookup protein, named module, named GO, cell type, metadata targeted rows only
analytical run summary, interpretation, cross-modal synthesis broader bounded evidence
explicit attachment, pin, or explicit artifact question authoritative explicit input plus bounded retrieval

Protein symbols, module names, and common cell types are extracted deterministically. Common scientific acronyms such as FDR, GO, WGCNA, RNA, and DNA are excluded from protein-symbol routing.

A missing entity is a valid zero-result outcome. Standard sends the run card and an empty evidence block instead of substituting unrelated rows.

Relevance fallback for unmatched data questions (deferred layer #3)

Keyword routing is a fast path, not the whole story. A scientific question phrased outside the enumerated keyword and entity lists used to route to general and ground zero run files even when it was a clear data question. The confirmed example is “Which proteins rise and fall in lockstep across samples?”; another is “What are the biggest abundance changes between conditions?”, which matches no protein symbol, no module/cell/GO keyword, and no run-summary cue, so the keyword router alone returns the run card with no rows. Adding more synonyms did not generalize — the next paraphrase failed the same way — because the synonym list was an all-or-nothing routing gate.

When, and only when, keyword routing yields general for the reason unmatched (that is, not a definitional or product/help question), the sidecar runs a deterministic Okapi BM25 lexical relevance pass over the run's own artifacts. Each artifact becomes a document built from its relative path, its column names, a per-family scientific concept profile, and a bounded cell sample; the question is tokenized with the same light stemmer. An artifact is eligible only if it shares at least one discriminative term with the question — a term whose inverse document frequency clears a floor — so ubiquitous words such as “data”, “run”, or “gene” cannot by themselves promote a file. The top-ranked families (at most three) are grounded through the same schema-aware retrieval, scoring, budgeting, and citation path as keyword routes, and the BM25 score is added as a ranking bonus so the lexically matched artifact outranks any incidental same-family candidate. Turns selected this way are reported with route lexical and carry a per-file “why selected” reason naming the matched terms and BM25 score.

This is purely additive and finishes the relevance layer the original design deferred. The curated keyword fast-path still handles its cases at zero retrieval cost; the BM25 pass runs only on otherwise-zero-grounding data questions. The same per-family concept vocabulary that was a brittle gate now acts as a graded ranking signal — a missing synonym lowers a score instead of dropping the turn to zero files.

Invariants preserved. The fallback adds no model call, no embeddings, and no persistent index; BM25 statistics are computed per run and cached by the same artifact-index signature the run card uses. Retrieval stays inside the selected completed run and remains schema-, row-, cell-, and token-bounded. Definitional and product/help questions never reach it, and if no artifact clears the discriminative floor the turn still grounds zero rows — so “What does FDR mean?” and off-topic questions (“book me a flight to Boston”) do not regress into dumping data. Genuinely semantic leaps with no shared vocabulary (true synonymy without lexical overlap) remain beyond BM25 and are the future embedding layer's job; open-ended hypothesis-driven orchestration stays reserved for Deep Research.

5. Schema-aware retrieval

The sidecar scans visible text/tabular run artifacts and classifies them by normalized columns before using filename hints. The implemented families are:

  • differential expression;
  • module assignments and hub/kME data;
  • module-trait correlations;
  • GO enrichment;
  • cell-type enrichment;
  • sample metadata;
  • run metadata.

This makes a file such as odd/names/alpha.csv retrievable as differential-expression evidence when its columns are gene, log2fc, pvalue, adj_pvalue, even though its filename has no biological hint.

CSV/TSV parsing handles quoted delimiters and embedded newlines. .txt delimiters are inferred from content. Every resolved path must remain below the selected completed-run directory. ai_insights/, R serialized state, scripts, and arbitrary paths are not retrieval inputs.

Retrieval behavior

  • Protein lookup filters exact symbol-bearing rows across DE and module-assignment families.
  • Module lookup filters module rows and ranks kME/hub scores descending when present.
  • GO lookup filters named modules and ranks FDR/adjusted p-value/p-value ascending.
  • Cell-type lookup filters named cell types and ranks significance ascending.
  • Cross-modal lookup first resolves significant cell-associated modules, then filters GO evidence to those modules.
  • Summary questions take statistically ranked slices from multiple evidence families.
  • Unmatched data questions enter through the BM25 relevance fallback (§4), which selects the evidence families and adds a relevance bonus to candidate scoring; row selection within those families then uses the same statistical ranking as every other route.

Canonical stageN/ outputs and stronger schema matches receive a deterministic priority bonus. Candidate chunks then receive family alignment, entity overlap, canonical-path, and row-density scores. Sorting occurs before the evidence budget is applied.

How rows are picked within a table

Row selection performs no statistics; it is a named-column numeric sort, and it is identical for keyword and lexical routes. After any entity filter (which is skipped on the lexical route, because that route has no extracted entity), the rows of each selected table are ordered in two steps:

  1. Find one sort column by name. The code scans a fixed priority list against the table's normalized column names and takes the first that exists: kME then hub_score for module-assignment tables, otherwise fdr, adj_pvalue, padj, pvalue. If none of those names is present, the column index is -1 and sorting is skipped.
  2. Sort by that cell's numeric value. Each row's value in that one column is parsed as a number; rows are sorted ascending for a p-value/FDR column (smallest first) or descending for kME/hub_score (largest first). Cells that are not numbers sink to the bottom.

The first 60 rows of that ordering are emitted (capped further by 16,000 characters per table and 2,000 bytes per cell); each emitted row's original line number becomes its citation.

Worked example — a differential-expression table:

gene,log2fc,pvalue,adj_pvalue,direction
CLU,-0.2,0.2,0.3,down
APOE,1.4,0.0001,0.002,up
APP,0.8,0.003,0.02,up

sort column -> adj_pvalue   (first match in fdr / adj_pvalue / padj / pvalue)
values      -> CLU 0.3 | APOE 0.002 | APP 0.02
ascending   -> APOE (0.002), APP (0.02), CLU (0.3)
emitted     -> top 60 of that order (here, all three rows)

So “most significant first” means only “smallest value in the p-value/FDR column first”. The reading of that as significance comes entirely from the pipeline convention of naming the column fdr/adj_pvalue/pvalue and storing a smaller-is-stronger number in it; the sorter itself computes and verifies nothing. Two consequences follow:

  • It depends on the column name. A table that stores its adjusted p-value as, say, q_value, BH, or p.adjust matches none of the recognized names, so no sort runs and the first 60 rows are taken in file order. The recognized-name list is fixed.
  • A table with no recognized column is never reordered (for example sample metadata): its top-60 is simply whatever order the rows already have in the file.

This is also why a lexical-fallback turn returns a table's most statistically significant rows rather than rows matched to the question's wording: the query decides which table, but within the table the ordering is this fixed numeric sort — it is not, for instance, re-sorted by log2fc magnitude just because a question said “biggest”. Query-aware row ranking is recorded as future work in Appendix C.

6. Bounds and truncation

Current values are evaluation-tuned defaults, not scientific constants:

Bound Current value
Lookup evidence budget 8,000 estimated tokens
Explicit-context evidence budget 12,000 estimated tokens
Lexical-fallback evidence budget 12,000 estimated tokens
Analytical evidence budget 16,000 estimated tokens
Absolute accepted override ceiling 24,000 estimated tokens
Lookup rows per candidate 30
Analytical rows per candidate 60
Candidate body ceiling 16,000 characters
Pre-read candidates per family 6
Selected chunks per family 2 for lookup/cross-modal; 3 for broad synthesis

Token estimates use four characters per token for routing and budget control. Billing and operational usage use provider-reported values instead.

The lexical fallback uses Okapi BM25 with k1 = 1.5 and b = 0.75, an inverse-document-frequency anchor floor of 0.7 (a query term must appear in fewer than roughly half the run's artifacts to promote a file), promotes at most three evidence families per turn, reads at most 32 KB per artifact into its index, and caps each artifact document at 4,000 tokens. These are deterministic, evaluation-tuned defaults, not scientific constants.

The grounding manifest records candidate count, selected paths/families, relevance scores, rows returned, included characters, and truncation. File and row IDs become citations.

7. Standard policy boundary in Pi

capabilitiesForPolicy() is applied while the Pi session is constructed, not merely described in a prompt.

Capability Standard Deep Research seam
Pi session/runtime yes yes
model switching, streaming, persistence, cancellation yes yes
run-card and server-side retrieval yes future policy may broaden
Pi skills no developer-gated seam retained
arbitrary read no developer-gated seam retained
Bash/Python no developer-gated seam retained
write/edit/save-artifact no developer-gated seam retained

The Standard resource loader explicitly overrides skills to an empty catalogue. Its Pi tools array is empty. If a conversation changes policy, the existing live session is disposed and rebuilt so capabilities cannot leak across policies.

No Standard retrieval tool is exposed in this implementation. Initial server-side retrieval was sufficient for the evaluated questions, so the optional one- or two-round escalation mechanism was intentionally not added. This keeps normal Standard answers at zero tool calls.

8. Prompt composition and caching posture

The composed provider input is ordered as:

  1. stable SignalFold grounding/security policy;
  2. policy and allowed external-source declaration;
  3. stable compact run card;
  4. dynamic retrieved evidence;
  5. restored compact history and authoritative pins;
  6. current question last.

This ordering gives provider/Pi prompt caching a stable prefix without using caching as a retrieval substitute. Pi/provider usage is recorded as uncached input, cache write, and cache read. Pi 0.79.9 does not expose a reliable standalone count for its generated system/tool-definition block, so that value is not guessed or mislabeled; the composed policy/run-card/evidence/history/question estimates and provider totals are reported separately.

Full prompt content is emitted only when developer mode is enabled. Normal telemetry carries the SHA-256 hash and grounding manifest. Operations retention remains bounded by the configured newest-turn limit.

9. Conversation history

History has two layers:

  • Pi performs its built-in live-session auto-compaction near the active model’s context threshold. Compaction start/end and token metadata are recorded as history events.
  • When a session is cold or restored from durable storage, compactConversationHistory() deterministically condenses old messages, keeps recent turns verbatim, and preserves pinned findings, decisions, hypotheses, citations, unresolved questions, and current research focus.

Pinned prior answers are also reinjected into warm turns as authoritative context, so a pin made after the original answer is not lost merely because Pi already has a warm session.

10. Attachments, citations, provenance, and export

Text attachments continue to be resolved by the server, path-confined to the run AI root, size-bounded, and wrapped as untrusted data. Their markers force the explicit route, and their content remains authoritative for the current question.

Grounding citations contain relative file path, artifact family, and included row IDs. The server persists those citations with the assistant message and persists a provenance entry for every selected artifact, including route, family, score, returned-row count, and truncation. Conversation export now includes citations and provenance instead of dropping them.

11. Operational telemetry

The implementation separates:

  • composed prompt characters and SHA-256;
  • stable policy tokens;
  • run-card tokens;
  • retrieved-evidence tokens;
  • history tokens and compaction state;
  • question tokens;
  • retrieval route and intent;
  • candidate and selected artifacts, scores, rows, and truncation;
  • per-model-call uncached input, cache write, cache read, output, cost, and tool-result count;
  • cumulative uncached input, cache write, cache read, output, model-call count, cost, and total context processed.

inputTokens on the final usage frame now means new/uncached input. Cache-read tokens are not silently added to it. totalContextTokens is the cumulative sum of uncached input, cache writes, and cache reads across Pi loop calls.

12. Security and failure behavior

  • Standard has no model-invocable filesystem or execution capability.
  • Server-side reads require a relative path confined to the selected completed run.
  • Retrieval has file, family, row, cell, candidate, and token bounds.
  • User/attachment strings still pass through existing inspection and output scrubbing.
  • Missing or malformed optional metadata produces null/empty orientation fields, not a turn failure.
  • Missing evidence produces an explicit empty evidence set.
  • Provider failure, cancellation, timeout, isolation, BYOK, and cost persistence remain in the shared runtime/server path.

What the selection eval measures

The eval scores the file-selection decision in isolation, with no provider/model call. It runs a fixed gold set of 18 questions through (a) the keyword router alone — the “before” — and (b) the router + BM25 fallback — the “after” — and checks each turn against a hand-labelled expected outcome. Filenames in the synthetic run are deliberately uninformative (odd/names/alpha.csv … ), so a pass reflects column-schema and lexical relevance, never a filename hint.

The 18 questions are chosen to expose the keyword-routing failure mode and prove it is fixed without collateral damage. 11 should ground run rows; 7 should stay general (zero rows):

Appendix C. Further improvements identified during this work

These surfaced while building the BM25 fallback and tracing how rows are selected. They are candidates, not commitments — recorded for planning, not yet scoped or validated. Each notes where it belongs and its rough cost. The heavy agentic / hypothesis-driven orchestration and dual-provenance evidence graph from the origin brainstorm stay Deep-Research-only and are deliberately excluded here.

ImprovementWhat & whyType / cost
Query-aware row ranking Within a selected table, order rows by relevance to the question — detect an implied metric (“biggest” → sort by log2fc magnitude; “lowest p” → p ascending) or lexically match row cells to the query terms — instead of the single fixed p/FDR sort. Directly addresses the §5 limitation: today the query picks the table, not the rows. Standard, deterministic; no model call.
Broaden & harden sort-column recognition The recognized statistic-column names are a fixed list (fdr/adj_pvalue/padj/pvalue, kME/hub_score). Tables that use q_value, BH, p.adjust, FDR_BH, etc. match nothing and silently fall back to file order. Add synonyms and/or a “numeric, bounded to [0,1]” heuristic, and surface when no sort column was found instead of falling back silently. Standard, deterministic; low effort, low risk.
Per-run semantic (embedding) relevance BM25 matches shared vocabulary only; true synonymy with no lexical overlap stays out of reach. A cached per-run embedding index over artifact descriptions, columns, and representative rows would catch those. The origin brainstorm's “embeddings later”. Future; needs a local or cheap-provider embedding model plus a small vector store and a build step.

Brainstorm item #4. Future; pipeline-side change — pipeline-owned files are outside the sidecar's edit scope, so this is a cross-component ask.
